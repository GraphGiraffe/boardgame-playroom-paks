# Автору пака · API 4 / UI 3

Все актуальные паки используют `manifest.execution: "isolated-v1"` и `sdkFeatures: ["isolated-execution-v1", ...]`; старое приложение отклоняет неизвестную возможность до загрузки точек входа. Правила и декларативное представление поставляются как данные `files["sdk/source.json"]` внутри обычного устанавливаемого `playroom-pack`; `rules.js`, `view.js`, `styles.css` содержат фиксированные неисполняемые маркеры. Приложение исполняет гостевые модули в VM и показывает сцену общими доверенными компонентами. Полнота конкретных экранов, обучения и иллюстраций проверяется отдельно от упаковки.

SDK-студия использует `sdk/project.json`: rules/presentation/helpers, необязательные types/support, начальные options. `support` сохраняет учебные определения, иллюстрации и звуковые каталоги; эти модули никогда не исполняются в host. `sourceModules` остаётся источником структуры слоёв и локалей. Инструменты находятся в соседнем canonical utils:

```sh
python3 sdk.py --app ../playroom new /tmp/my-game --id my-game --packs ../playroom-paks
python3 sdk.py --app ../playroom adopt ../playroom-paks/packs/gofish --packs ../playroom-paks
python3 sdk.py --app ../playroom compile /tmp/my-game --packs ../playroom-paks --output /tmp/my-game.playroom-pack.json
```

`new` записывает фактическое происхождение от шаблона; `adopt` записывает принятие существующего исходника, исходную версию и SHA manifest, увеличивает patch при смене execution и не делает это повторно. Он не утверждает, что исторические игры создавались генератором. Обе операции ведут в один read-only source loader и compiler. `compile` выполняет SDK static/type check, аудит фактического набора ресурсов и выдаёт устанавливаемый пак; существующий output не перезаписывается. `build` команды SDK остаётся исходным экспортом `playroom-sdk-source`, который устанавливать нельзя. Для коллекции: `python3 build.py --include-sdk-examples --output-dir /tmp/playroom-build`.

Полный UTF-8 JSON устанавливаемого пака ограничен 4 000 000 байт, цель — 500 000; ресурсы — 2 000 000 байт / 512 файлов. `assets/*.json` проходит проверку SDK-анимации и учитывается в ресурсном бюджете; `config/*.json` остаётся отдельными инертными данными. Markdown/text-заметки перечисляются в аудите, но не в runtime-ресурсах. В бюджет входят выбранные shared skins и их зависимости, медиа, чистые исходники, типы, локали, manuals и support-модули. Manifest asset-pack и его runtime files сохраняются в `resourceClosure`; JS/CSS providers остаются инертными исходниками. Для персонажей включаются ровно runtime SVG из manifest.items, без архивных detailed masters и повторных data-URL каталогов. Исходный архив сохраняет masters и авторские файлы. SDK sourceHash совпадает с Node по порядку dependencies → rules → helpers → presentation → types → support и дополнительно связывает config, media digests/provenance, shared manifests, provider и rulebook metadata. Изменение любого ресурса делает прежний SDK checkpoint несовместимым. SHA устанавливаемого пака покрывает все bytes контейнера.

Текущая политика: поддерживается актуальная связка приложения и паков. Обновление пользователей с 0.19+ сохраняется; старые Online-комбинации не сопровождаются. После успешной установки текущих игр несовместимые сохранения удаляются, без переноса или экспорта. Ниже описаны форматы данных и внутренние контракты, а не обещание сопровождения прежних выпусков.

Текущая связка документации: коллекция **0.9.0**, ХОД **0.21.0**, engineApi 4 / viewApi 3. Старые номера в описании происхождения не меняют текущий контракт.

Перед изменением ресурсов и UI: [инварианты упаковки, скинов и проверки ошибок](DEVELOPMENT-REGRESSIONS.md). Исходники не являются составом готового пака.

## Слои

Сначала прочитайте [карту архитектуры и владельцев состояния](ARCHITECTURE.md). Для обучения — [контракт сценариев и пользовательского прогресса](https://github.com/GraphGiraffe/boardgame-playroom/blob/main/docs/TUTORIALS.md).

`packs/<id>/manifest.json` — метаданные/версии/режимы/доступные места/settings/capabilities/sourceModules. `domain/` — чистые правила. `presentation/` — SceneModel, ActionChoice labels и Event presentation после projection. `locales/ru/` — тексты. `rules.js` — только регистрация Definition в SDK. `sdk/project.json` объявляет guest-модули; `presentation/rule-illustrations.js` задаёт чистые публичные арты. Авторских `view.js`/`styles.css` в текущих играх нет: DOM и стили принадлежат общему renderer приложения. Необязательные assets поставляются локально.

Эталоны: **tictactoe** (простое поле/полная модель), **dice-poker** (публичные кубики/таблица/подтверждение), **gofish** (скрытая рука и публичные события), **private-counter** в examples (не входит в коллекцию).

```json
{"sourceModules":{"rules":["domain/game.js","presentation/scene.js"],"view":["presentation/scene.js","presentation/tutorial.js"],"locales":{"ru":["locales/ru/game.json"]}}}
```

GameModel Definition contractVersion=1: create/validate/actions/reduce/project/result/bot, дополнительные score/observe/reactions и decisionWindow при необходимости; GameModel.start — метод runtime, начальные события возвращаются из create. actions возвращают command + visibility; reduce возвращает position/events/turnEnded и при объявленном цикле roundEnded. Actor и viewer различать. RNG хранить в состоянии и передавать явно; бот видит разрешённую проекцию/память, не неизвестные карты.

При создании через лобби `create` получает `options.seatIndices`: номера исходных физических мест в порядке игроков, без пустых слотов. Это отдельный публичный контекст создания, не поле метаданных игрока. Используйте его для соответствия команды раскладке `teamLayouts`; прямое создание модели может задавать последовательные места по умолчанию. Командные ID и роли цвета системы: blue, red, cyan, brown (`team.*`), в том же порядке. Лобби показывает медальоны и на пустых слотах по объявленной раскладке.

Раскладка Стихий для трёх команд: Синие — 1/3/5, Красные — 2/4/6, Голубые — 7/8 (и 9 в играх с девятым местом). Для четырёх: Синие — 1/3, Красные — 2/4, Голубые — 5/7, Коричневые — 6/8. Индекс игрока после удаления пустых слотов не заменяет физический номер места. Доменные команды и `teamLayouts` проверяются на совпадение.

`result.playerOrder` необязателен: полная перестановка всех индексов игроков для упорядочения участников внутри одинакового места. Места и победители остаются отдельными фактами результата. Поле `order` у метрик по-прежнему означает `asc`/`desc`, а не перестановку. Приложение размещает командный жетон или жетон первого игрока на аватаре, медаль места — отдельно.

Domain события — typed facts с visibility; presentation добавляет MessageRef, speech/notice/sound/feedback/reveal/sequence. Сначала privacy, потом перевод и Web. Полное состояние не передаётся гостю и не прячется CSS. Описание событий/метрик/прогресса — [SDK 0.18](https://github.com/GraphGiraffe/boardgame-playroom/blob/main/docs/SDK-0.18.md).

## Сохраняемое состояние

Необязательный чистый `storageState(data)` в GameModel Definition возвращает
данные для долговечного checkpoint. Допустимо исключать только вычислимые
данные представления: Mage возвращает `{...data, frames: []}`. Игровые позиции,
руки, приватные подтверждённые планы, RNG и всё, что влияет на последующие
правила, должны сохраняться. Нельзя изменять исходный `data` или обращаться к DOM.
Без этого порта состояние сохраняется целиком. Живой runtime не теряет кадры.

История восстанавливается из начального состояния и принятых команд по запросу,
заново создавая эффекты; последнее нормализованное состояние сверяется с checkpoint.
Возобновление загружает checkpoint напрямую, без replay. Специфичные исключения
принадлежат паку, общий runtime не знает ID Mage или имён его полей.

## UI

`PlayroomViews.register` принимает renderer элементов сцены. Общие Source/Target/Hand/BoardTarget/ScoreTable/Avatar/Reveal обслуживает приложение. Пак не рисует собственную шапку/toolbar/карточки игроков. Fixed scene default; один флаг allowLayoutChange может принадлежать только конкретному действию. Правила не зависят от DOM.

Рука прокручивается с любой карты, скрытые передачи рубашкой, публичные пары/сеты раскрываются общим reveal. Мини-руки обрезаны и перекрываются во всех рассадках. Доска с fieldSizing=fit сохраняет fieldAspect. Метрики/бейджи семантические, не распознаются по тексту. Скин меняет оформление после projection, не действие и не RNG.

## Версии и выпуск

Неизменяемая packVersion при публикации; stateVersion меняется при форме данных, engineApi — при SDK. Поставки должны сохранять точные старые версии. Asset pack dependencies также точные. ## Метаданные редактора правил

Необязательное `settings[].control` принимает `slider` или `select`; без указания сохраняется список. У слайдера позиции соответствуют порядку `options`, а сохранённые значения остаются `options[].value`, включая строковый `0` для отсутствия лимита. `label` и `help` задают подпись и справку. Колоды используют `select`.

`presetSetting: {label, help, control, options: [{value, label}]}` переименовывает и упорядочивает выбор preset в редакторе, не меняя domain IDs или значения по умолчанию. `ruleGroups: [{label, fields: ["preset", "deck"]}]` задаёт смысловые блоки по две ячейки в строке; `fields` ссылается на preset или settings key. Флаг `end: true` переносит блок завершения в конец после общих параметров. Каждый параметр перечислять один раз. Отсутствующие в группах поля сохраняются в редакторе, единственный вариант скрывается. `visibleWhen` проверяется по точным значениям правил, а не индексам слайдеров. Это метаданные Web UI, без изменения engineApi/viewApi/stateVersion.

#### Компактные иллюстрации параметров

Иллюстрация — необязательные публичные данные автора, не HTML, JavaScript, URL или новое правило игры. По умолчанию любой параметр компактен: название, одна иллюстрация выбранного значения, подпись и небольшие варианты выбора. При отсутствии подходящей иллюстрации хост показывает текст; неизвестное значение не подменяется предположением по ID игры, названию или ключу поля.

`settings[].preview: {kind: "cards" | "dice" | "health" | "lives"}` выбирает общий компонент: карты, кубики, сердца или фишки жизней. Для числового `option.value` количество берётся из этого значения. `options[].preview` наследует `kind` поля либо задаёт его явно и может содержать `count` (целое 0–100) или `countFrom` — но не оба сразу. Например, обычный preset выбора размера руки остаётся компактным:

```json
{"presetSetting":{"label":"Карт на руке","options":[
  {"value":"quick","label":"5","preview":{"kind":"cards","count":5}},
  {"value":"classic","label":"7","preview":{"kind":"cards","count":7}}
]}}
```

Зависимое авторское значение описывается таблицей, а не формулой домена в UI. У поля здоровья `{preview:{kind:"health"}}` вариант «Авто» может содержать:

```json
{"value":"mode","label":"Авто (3 / 4)","preview":{
  "countFrom":{"field":"actionsPerTurn","values":{"1":3,"2":4}}
}}
```

Ссылка `field` обязана существовать среди `settings`; ключи `values` должны быть ID его вариантов. Таблица содержит 1–16 записей, значения — целые 0–100. Хост пересчитывает иллюстрацию при выборе зависимого параметра; при неизвестном контексте оставляет текст, не делает догадок.

`options[].description` — короткое описание именно выбранного варианта; подробности остаются в `field.help`. Рекомендуется одна фраза до34–40символов для обычной карточки, до70для широкой карточки режима; технический предел —360символов. Сокращайте авторский текст по смыслу, не скрывайте его через line-clamp. Хост всегда экранирует текст. Например, для исходной колоды36/52в «Акулине» значение и подпись остаются36/52, но явный `preview.count` равен35/51: описание объясняет, что дама треф удалена. Не считайте размер поля, число рангов или число пар количеством карт начальной руки.

Ещё два общих типа используют существующие компоненты приложения, без ветвления по ID игры:

- `preview:{kind:"declaration",actor:"human"|"bot",label:"UNO!"}` — миниатюра игровой кнопки и индикатор ручного/автоматического объявления. `label` — непустой текст до24символов. Общие `kind`/`label` можно объявить у поля, а `actor` — у каждого варианта.
- `preview:{kind:"symbol",icon:"undo"}` — конкретная смысловая пиктограмма общего UI. Список разрешённых ID: `undo`, `first`, `people`, `shuffle`, `rules`, `player`, `bot`, `trophy`, `clock`, `eye`, `eye-off`, `hand`, `board`, `ship`, `cards`, `dice`, `check`, `close`, `play`, `pause`, `history`, `stop`, `grid`, `teams`, `shield`, `sword`, `refresh`, `star`, `pieces`, `solitaire`, `lock`, `unlock`. Другие имена, HTML, URL и произвольные SVG в `preview` отклоняются.

`preview:{kind:"illustrations",ids:["setting-card-fire-attack","setting-card-water-movement"]}` показывает1–4публичные иллюстрации зарегистрированного представления через существующий `Views.illustration(game,id)`. ID —1–64символа из `A–Z a–z 0–9 . _ -`; повторы разрешены для примеров одинаковых действий. Поле может объявить только `kind`, каждый вариант задаёт `ids`; raw HTML, URL и произвольные SVG в manifest запрещены. Требуется отдельный `sdkFeatures:"parameter-illustrations-v1"` (элемент массива) и приложение0.21.0-preview.70, его объявляет каждый пак, использующий этот вид иллюстраций. Представление должно возвращать реальные игровые компоненты/значки без доступа к приватному состоянию; alias в паке переиспользует тот же renderer, не копию рисунка. Хост не разбирает доменные названия ID и не выбирает действие за пак. Общий числовой вариант/описание остаётся в option label/description.

Вариант наследует поля `preview` своего параметра и может явно уточнять их; итоговые данные проверяются до выполнения пака. Один смысловой символ с коротким объяснением предпочтительнее декоративной общей иконки настроек. Количество показывается картами/кубиками/жетонами только тогда, когда действительно означает эти объекты в правилах.

`presentation:"mode"` у `presetSetting` или одного поля `settings[]` явно разрешает крупную иллюстрацию структурно отличающихся режимов. На весь manifest допускается не больше одного такого поля. Каждый вариант должен иметь корректный явный или унаследованный `preview` существующего вида; например, `symbol` для вариантов правил. Только у такого поля разрешены также `preview:{kind:"fleet",pieces:[4,3,3,2,2,2,1,1,1,1]}` и `preview:{kind:"teams",teamSizes:[2,2]}`. Это состав флота/схема режима из публичных правил, не текущая расстановка или состав живой комнаты. `pieces`: 1–16 целых размеров 1–16, сумма до100; `teamSizes`: 1–8 групп по1–32, сумма до32. Число карт 5/7, здоровье, жизни и количество кубиков никогда не требуют такого hero-флага. Произвольные дополнительные поля в `preview` отклоняются компилятором и загрузчиком. Обновление этих метаданных требует новой версии изменённого пака, но не меняет engineApi/viewApi/stateVersion или сетевой протокол.

Поля `settings[].presentation:"mode"`, `inactiveWhen` и `inactivePresentation` требуют `sdkFeatures:["local-input-v1","turn-order-v1","parameter-previews-v2"]` и приложение 0.21.0 в текущей стабильной линии. В коллекции0.8.10 эта дополнительная возможность нужна только Дураку и Косынке; обычные краткие пояснения остальных паков её не требуют. Обновляйте приложение первым. Это feature guard интерфейса, без изменения engineApi/viewApi/stateVersion/сетевого протокола. Старое приложение .67 не умеет предварительно отфильтровать новый feature по каталогу; импорт требует обновления приложения.

Зависимый неактивный параметр может задавать `inactiveWhen:{scoring:"vegas"}` и `inactivePresentation:{preview:{kind:"symbol",icon:"lock"},description:"Vegas: по 1 — 1 проход, по 3 — 3."}`. Оба поля обязательны вместе: условие содержит1–16ссылок на существующие settings и их option IDs (точное совпадение всех значений); иллюстрация использует тот же проверяемый `preview`, описание — тот же ограниченный экранируемый текст. Хост оставляет карточку на месте, выключает редактирование и исключает её значение из отправляемых параметров, но сохраняет исходный выбор в черновике. Неактивный вид поясняет публичные правила; фактическое значение по-прежнему определяет domain. При снятии условия восстанавливается прежний вариант, без молчаливой перезаписи.


В новых играх Рыбы/Акулины колода 54 не предлагается. Акулина показывает число карт в партии — 35/51, сохраняя внутренние deck IDs 36/52. Domain сохраняет чтение старых состояний с 54 картами; точные прежние опубликованные паки не переписываются.

## Скины компонентов

`skinFamilies: ["card-face", "card-back"]` перечисляет применимые типы, `defaultSkins: {"card-face":"mini-split"}` задаёт исходный вид. Индивидуальный выбор пользователя и явно выбранный Основной имеют приоритет. Настройки хранятся локально в приложении; пак не создаёт своё хранилище и не добавляет скин в правила/сохранение. Renderer использует общий asset resolver с контекстом пака. Типизированные метаданные проверяются compiler/runtime; новая metadata опубликованного пака требует новой packVersion.

Новые исходные паки `spider` и `klondike` используют общий чистый `shared/domain/solitaire.js` и `solitaire-board` без очередности ходов. Подсказки вычисляются из разрешённых публичных действий, не из запаса/истории authority.


### Читаемые зоны карточного скина

`shared/assets/catalog.json` → `card-face.stacking[variant]` хранит `protectedZones` (x/y/width/height в долях лица), минимальную открытую долю `horizontal`, `vertical`, `arc`, шаг рубашек `faceDown` и направление `wasteAxis`. Цветовые варианты используют одинаковую геометрию. Эти данные принадлежат ассетам, не правилам игры. Большой центральный знак требует большего открытого участка, чем компактный угловой индекс.

`helpers.assetLayout('card-face')` возвращает параметры активного скина для текущего пака. SVG лица также несёт `data-card-stacking`: общий fitter руки/веера и горизонтальных стопок использует минимум открытой доли; при нехватке места сохраняется прокрутка. Пасьянсы получают из тех же метаданных вертикальный шаг и направление сброса. Поле игры определяет раскладку, ассет — ограничения перекрытия. Переключение скина не меняет состояние партии.


Карточные сцены (`family:'cards'`) получают цвет поля от приложения: светло-зелёный/тёмно-зелёный по текущей теме. `PlayroomShared.cardSlot({label,suit,kind,attrs,className})` отображает пустое место карты, при заданной масти используя активный скин; `kind` описывает существующую игровую зону, не создаёт действие. Для локальной ошибки предусмотрен `data-feedback-required="<selector>"`: Input подсвечивает выбранные элементы внутри текущей сцены и не отправляет игровую команду. Предикат запрета и selector задаёт renderer из доступных действий и публичного состояния.


Колода персонажей: `character-face` — отдельное семейство от `card-face`. Сцена Пексесо выбирает актуальное семейство по типу колоды; демонстрационный объект для всех трёх вариантов — `circle-red`. Общие наборы персонажей сохраняют ID фигур/цветов и не влияют на пары или правила. Наборы аватаров используются приложением отдельно от предпочтений скинов пака.

### Подготовленная сборка и исходники

Компилятор хранит domain/presentation/locales модули один раз в `files["sdk/source.json"]`; media closure содержит только фактические ресурсы. Старые provider JS/CSS сохраняются при необходимости как инертные source-fidelity записи и не исполняются ни host, ни VM. Имена `rules.js`/`view.js`/`styles.css` в контейнере заняты фиксированными маркерами. Исходники остаются в репозитории и source ZIP. Авторские .md/.txt из assets не входят в runtime. Аудио хранится в assets/ один раз: sounds.js задаёт метаданные и получает src через PlayroomPack.asset, без второй base64-копии. Подробные персонажи characters — архивный набор; рабочие стили minimal («Стандартный») и simple («Простой»).

## Стандартные размеры

Основные карты, кубики, костяшки и фишки используют роли `--size-card`, `--size-die`, `--size-domino`, `--size-token`; миниатюры — отдельную роль. Не увеличивайте основную карту через ширину контейнера. Стили используют стандартные `--size-space-*`, `--size-type-*`, `--size-radius-*`, `--size-length-*` с fallback для автономного пака. Канонический каталог хоста — `core/size-tokens.json`, описание — app `docs/SIZE-SYSTEM.md`. При одинаковом viewport/ступени основной размер карты не зависит от game ID. Клетки доски и внутренние SVG-координаты производны от стандартного artboard; нестандартные базовые размеры требуют объяснения.

### Размерные роли, поведение и будущие зоны

Хост предоставляет `--size-*` и `--ui-duration-*`; автономные CSS fallback обязательны. Коэффициенты `stacking` и `protectedZones` остаются в манифесте скина: горизонтальное/вертикальное раскрытие, дуга, faceDown и ось сброса не заменяются произвольным паковым масштабом. UI-обводки в экранных px и SVG rim в viewBox имеют разные единицы.

Существующие `family`, `layout.focus`, `surface`, `actionReserve`, `playerContent.counters/badges/indicators` задают состав зон; общая раскладка не должна знать ID игры. Контекстные действия с участником и подтверждение цели не должны сдвигать fixed field или перекрывать доступные цели. Новые группы смешанной руки, inspect, вращаемые/исследуемые тайлы описаны в проекте контракта `playroom/core/size-tokens.json:extensibleZones`; это пока не новый API и не реализация правил. Не передавать скрытые лица/URL ради увеличенного просмотра или анимации раскрытия.

## Общие кнопки и короткое название

`manifest.json` поддерживает необязательный `shortName`: непустую строку до 60 UTF-16 единиц. Например, `"name":"Терраформирование Марса","shortName":"Марс"`. Полное имя остаётся именем игры; Web-шапка сначала уменьшает его шрифт до разумного минимума, затем использует короткое имя и, если нужно, многоточие. Проверка поля одинакова в компиляторе и импортере приложения.

Renderer использует `H.button({icon:'play',label:'Играть',variant:'game',attrs:'data-action="roll"'})`: иконка идёт перед подписью. Можно опустить иконку или подпись; для одной иконки задать `ariaLabel`. Варианты: `primary`, `secondary`, `danger`, `plain`, `outline`, `game`; доступны `disabled`, `active`, `type`. Подписи экранируются; `attrs` содержит только доверенные атрибуты разработчика. Генератор и оформление принадлежат `shared/components/game-components.{js,css}`, геометрия задаётся общими токенами приложения. Не создавать отдельную копию стандартной кнопки в паке; карты, кубики и счётчики используют свои канонические компоненты.

Общие типы элементов, принадлежность окантовки типу колоды и независимые рубашки
наборов описаны в [PIECE-TYPES.md](PIECE-TYPES.md).

## Одновременный выбор и квадратные карты

Общие чистые модули `decision-window`, `tactical-grid`, `effect-batch`, `bot-policy` подключаются через `sharedDomain`. Окно публикует только ID, участников, готовность и версии; планы раскрываются по правилам пакета. Batch сохраняет отдельные причины падения и урона: падение имеет приоритет над лечением и определяет награду независимо от порядка регистрации урона. RNG профилей/ошибок отделяется от колоды; одинаковое решение в том же окне не разыгрывается заново.

Игра только для людей объявляет `capabilities.bots: false`: лобби не предлагает бота, движок отклоняет bot roster. Если признак отсутствует, боты поддерживаются как раньше. Боты описывают стратегии в presentation metadata. `auto` и `random` различаются; назначенный профиль сохраняется в Position. Новые параметры и окна необязательны для остальных паков. `cardFrame(...,{shape:'square'})` и `cardBack({shape:'square'})` используют общий card-deck. Высота руки и список игроков принадлежат host, не styles.css пака. `publicFrames` получает только разрешённые кадры; состояние и скрытые планы не зависят от показа фаз.

Mage Brawl основан на prototype `97d984a`, A/v3.0 с уточнениями v3.1: щит внутри цепочки и суммарное лечение/урон одной скорости. Добор выживших следует после явного выбора базы и добора возрождающихся. Сравнение фиксированных состояний хранится в companion `tests/fixtures/mage-brawl-reference.json`; оно не требует одинаковых Python/JS RNG.

`publicFrames` выводит первый публичный кадр сразу в HTML. Кадр может содержать `players` — разметку стандартных `H.playerPanel`, собранную из публичного снимка; `livePlayers` соответствует итоговому `live`. Начальный `playerContent` должен соответствовать первому кадру. `sound`/`pack` задают cue кадра. Контроллер синхронно переключает поле и стандартные панели, а приватная рука недоступна до итогового кадра. Начальный снимок создаётся до расходования карт и ульты, без планов. `PlayroomPublicSequence.defer(host, callback)` откладывает только окно результата, не авторитетные правила.


### Контракт участников сцены

`presentation.scene(projection)` возвращает ровно одного участника на каждый
индекс игрока: `{player, metrics}`. Поле `id` вместо `player` не допускается.
Индексы уникальны, находятся в пределах `projection.playerCount`; порядок массива
не задаёт идентичность. Метрики имеют уникальный в пределах участника `id`,
`kind`, конечное числовое `value` и `label` (MessageRef до локализации).
Для жетонов `display` задаёт `icon`, целую `capacity` от 1 до 64 и необязательный
булевый `overlap`. Значение жетона — неотрицательное безопасное целое;
`capacity` означает минимальное число слотов, поэтому накопленные короны могут
его превышать. SDK проверяет эти поля до перевода и передачи renderer, без
копирования поля и рук. Эти проверки не заменяют фильтрацию приватной проекции.

В API 4 это часть SceneModel вместе с EntityRef, геометрией зон и публичным
PresentationPlan. Поля правил renderer недоступны.

## Правила для новых игроков

Следуйте [структуре и проверке книг правил](PLAYER-RULES.md): цель → подготовка → ход → особые механики → завершение. Один локализованный элемент `rules` содержит заголовок первой строкой и абзацы следующими строками. Пояснения настроек и текущие значения приложение выводит отдельно в конце. Короткая памятка карты не заменяет полные правила. Проверять объяснение эффекта по domain, а не только по старой формулировке.

## Сложность ботов

Новые настройки участника: `botSettings:{strategy,difficulty}`, уровни `easy`, `medium` (по умолчанию), `hard`. Стратегия остаётся независимым выбором, если пак её предоставляет. Пятый аргумент `bot(projection,actor,commands,memory,context)` содержит `difficulty`, `depth`, `errorRate` и воспроизводимый `random()`. Сложность меняет оценку решений и шанс ошибки; сложный бот не безошибочен. Память Пексесо использует вероятности 35/18/6%, без периодической зависимости от номера хода.

Runtime применяет альтернативное решение того же типа; не дублируйте эту вероятность в паке. Для собственной модели ошибки объявите `botHandlesDifficulty:true`. `botMistakes` ограничивает допустимые альтернативы без доступа к закрытому состоянию. Точные контракты — SDK приложения. Для старых runtime используйте значения по умолчанию аргумента context. Автоматические действия человека не должны получать ошибки бота.

Сценарии обучения описываются чистой фабрикой в `presentation/tutorial.js` с внедрённым переводчиком. `sdk/project.json.support` подключает её в VM представления; сериализуемые цели и шаги показывает общий renderer. Фабрика не меняет модель, не обращается к DOM/storage/сети. [Границы приложения](https://github.com/GraphGiraffe/boardgame-playroom/blob/main/docs/DEVELOPER-ARCHITECTURE.md).

## Необязательные правила в Markdown

Можно задать правила в `metadata.rulebook` или написать Markdown в отдельном файле. Для нового SDK-пака сохраните `rules/ru.md` и добавьте в `sourceModules`:

```json
{"rulebooks":{"ru":"rules/ru.md"}}
```

Локаль должна присутствовать в `sourceModules.locales`. В SDK-паке студия и ХОД выбирают документ для текущего языка, затем для языка по умолчанию. `metadata.rulebook` служит запасным вариантом. В студии после сохранения Markdown нажмите «Перечитать код».

Студия, SDK `check` и сборщик используют один конвертер. Пак с Markdown требует Mistune 3 в локальном Python, например `python3 -m pip install 'mistune>=3,<4'`. Браузер получает готовые структурированные блоки. Каждый заголовок создаёт раздел оглавления. Поддержаны абзацы, жирный и курсивный текст, inline-код, плоские списки, таблицы и HTTP(S)-ссылки. Строка `![Подпись](illustration-id)` обращается к зарегистрированной игровой иллюстрации по ID.

Начинайте документ с заголовка. Raw HTML, внешние изображения, скриптовые URL, вложенные списки, цитаты и fenced code не поддерживаются: сборка сообщает ошибку, вместо того чтобы молча терять содержимое. Существующие правила не переводите автоматически. Новые справки могут переиспользовать тот же формат блоков; текущие динамические подсказки остаются на прежнем контракте.


### Частные переопределения компоновки ( SDK)

Стандартная компоновка принадлежит приложению. Пак описывает только изменённые элементы через `layout.overrides`, а не особую ветку по названию игры в движке. Допустимые параметры и примеры: [контракт SDK приложения](../../playroom/docs/PACK-SDK-LAYOUT.md). Морской бой переопределяет только положение оппонента и индикаторов; пасьянс объявляет колонки для своих стопок; Лудо объявляет якоря через `layout.seats`. Шапка, системные кнопки, основная геометрия карточки и безопасные зоны остаются общими. Произвольные ключи overrides отклоняются.


### Локальные допустимые действия и черновики (SDK local-input-v1)

Companion 0.8.10-preview.37 требует `sdkFeatures:["local-input-v1"]` в manifest и feature guard в bridge до регистрации. Приложение должно поддерживать feature (0.21.0-preview.60); engineApi 4 / viewApi 3 сохранены.

`definition.localChoices(projection)` возвращает `{command,visibility}` только из разрешённых `projection.data`, actor/audience/status/turn. Вызов на public Table не должен читать чужие карты. Хост по-прежнему вызывает `actions` / `reactions` на полном состоянии и проверяет каждую команду. `localData(projection)` при необходимости возвращает производные данные для presentation: предпросмотр геометрии, оценки или подсказки. `localReaction(projection,command)` описывает те же публичные эпизоды реакций; временные окна и управление участниками остаются у authority. Эти функции чистые, без DOM/часов/storage/RNG. Сетевой factsOnly-кадр не содержит `actions` и производных данных.

Не добавляйте вычисляемые поля в передаваемый intent. `derivedFields:{plan:["element"]}` позволяет правилам/представлению получить стихию по ID собственной карты, без повтора в команде. Для локального выбора используются те же компоненты, без таблицы всех сочетаний ходов.

`draft(projection)` может вернуть `mode:"sequence"`, `select`, `commit`, `count`, `cancel` либо `mode:"coalesce"`, `select`, `commit`, `max`, `delayMs`, `toggleKey`. `draftProjection(projection,actions)` накладывает только собственный локальный выбор на исходную проекцию. Примеры: Mage — два plan, unready отменяет первый; Ятзи — hold по index, roll/score подтверждают, delayMs=50. Максимум 16 действий; задержка не выше 250 мс. Промежуточные selectors на хосте обязаны не создавать события, менять RNG, завершать ход/раунд или игру. Команда `{type:"batch",actions:[...]}` валидируется пошагово и сохраняется одной транзакцией. Вложенные batch запрещены.

Черновики принадлежат приложению: они привязаны к сеансу/эпохе/игроку/его decision window, локально восстанавливаются после разрыва и не попадают в историю. Новый ход или изменённая собственная версия окна инвалидирует черновик. Успешная доставка всегда требует авторитетного ACK после сохранения.


### Общая индикация очереди (SDK turn-order-v1)

Движок вычисляет `scene.nextPlayer`, общий UI окрашивает карточку и общий Feedback удерживает прежние current/next до окончания показа действий. Пак не создаёт собственную базовую подсветку. Для последовательной игры по умолчанию используется цикл индексов игроков. Одиночная/завершённая игра, подготовка и одновременное окно не показывают фиктивную очередь.

Необязательный чистый `definition.turnOrder(authorizedProjection)` задаёт только особенности правил: `{players:[0,2,3],direction:-1}` — порядок без выбывших и направление; `{next:2}` — явный следующий, в том числе повтор текущего; `{next:null}` или `null` — следующего нет либо он ещё не определён. SDK проверяет уникальность/границы индексов/направление и выполняет обход. Хук не читает скрытые карты и RNG, ничего не меняет. Для неизвестного случайного/частного исхода не угадывайте фактический результат: базовая индикация показывает объявленную очередь, подтверждённый переход приходит с новой моделью.

UNO объявляет порядок живых игроков/направление, Домино/Лудо/Змеи — границы завершения, Go Fish/Старая дева — публично оставшихся участников, Дурак — роли очередного ответа. Mage не объявляет следующего при совместном планировании. Предпросмотр выбранного особого действия остаётся правилом пака и использует общий playerContent/Feedback, без специальных веток движка по ID игры.

Новые companion-паки требуют `sdkFeatures:["local-input-v1","turn-order-v1"]`. Обновляйте приложение до .62 прежде коллекции .39; общая команда «Обновить всё» соблюдает этот порядок.

Иллюстрация параметра вложена в кнопку переключения: внутри запрещены кнопки и другие интерактивные элементы, даже disabled/inert. Для составной схемы используйте один нормализованный SVG с `data-art-role="parameter-diagram"`, помещая настоящие игровые SVG через vector.place. Служебные контуры — currentColor, прозрачный фон; материальные игровые компоненты сохраняют свою палитру. Все выбираемые параметры должны иметь короткое пояснение варианта и смысловую иллюстрацию. Общие firstPlayerMode/seatOrder/endMode рисует хост одинаково для всех игр.
Плоскость параметра использует авторскую единицу как CSSpx; не рассчитывайте на автоматическое увеличение по содержимому. Стандартный стол120×72, карта36×50.4, кубик40×40, служебный одиночный значок44×44. Повторяющиеся элементы сохраняют размер при переключении вариантов; при большем количестве карты можно перекрывать. Хост центрирует рисунок в постоянной области, не увеличивая масштаб; широкий режим сохраняет отдельную область160px вместо обычных96px.

## Размер готового пака и SDK-ресурсов

Готовый устанавливаемый JSON ограничен 4 MB (4 000 000 байт UTF-8 до HTTP-сжатия), включая manifest, compiled/shared modules и base64. Для SDK source-export действует отдельный такой же hard limit и цель 500 kB с предупреждением, без нижней границы. Проверяйте оба формата: source-export не устанавливаемый player-pack. Канонические SDK check/build дополнительно ограничивают runtime-ресурсы 2 MB/512 файлов, изображения 512 kB, SVG/анимации 64 kB и аудио 128 kB; decoded-растры и длительность проверяются отдельно. Числа и границы проверки описаны в app `docs/PACK-SDK-STUDIO.md`. Source-мастера храните вне runtime assets, не удаляйте их для прохождения бюджета.


## Тексты и файлы паков

Исходники остаются отдельными файлами. Словари каждого языка находятся в
`lang/ru.json`, `lang/en.json` и указаны в `sourceModules.locales`.
Отображаемые поля manifest содержат ссылки `{ "key": "..." }`, а не русские
строки. В presentation/support используйте такие ссылки или `SDK.text(key,params)`
для мест, требующих строку. ID, enum value, пути и код не являются переводами.
Резервный язык задаёт `defaultLanguage`; в нём должны существовать все используемые
ключи. Недостающие переводы другого языка берутся из резервного.

Общий compiler при упаковке собирает `manifest`, `lang`, `sdk`, `files` в
`.playroom-pack.json` формата 2. `lang.ru` — объект с содержимым `lang/ru.json`,
а не ещё одна сериализованная JSON-строка. Полный SDK-source используется только
как внутренний порт; второго каталога `sdk.catalogs` в готовом паке нет.
Не редактируйте готовый sourceHash вручную: измените исходники и пересоберите.


Компактная схема использует `fields` и `groups`. В исходном манифесте укажите
`"settings": "settings.json"`, как в шаблоне `sdk/templates/turn-counter`.
Компилятор подставляет содержимое файла в `manifest.settings` готового пака.
В `Definition.create` настройки доступны в `options.options`. Для полей
`boolean`, `integer` и `number` SDK передаёт значение объявленного типа
и подставляет `default`, если выбора нет. Строковые ID остаются строками.
Локализованные тексты по-прежнему берутся из языковых каталогов.
Вариант может не иметь label, если она выводится из числа; общие подписи —
`{common:"yes"}`, `{common:"no"}`, `{common:"infinity"}` и т.п. Они принадлежат
словарю приложения. Для собственных формулировок используйте `{key:"..."}`.
Не переводите ID/option.value. Числовые величины хранятся данными:
`estimatedDurationMin:[20,40]`, `unit:"s"` на поле, `range:{min:30,max:180,step:1}`.
Повторяемые подсказки выносите в `optionDefaults.description`; отдельный вариант
может заменить её либо очистить через null. Ключи словаря привязывайте к имени
поля и value, чтобы перестановка вариантов не требовала переименования переводов.
