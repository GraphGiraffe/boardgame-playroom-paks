# Работа с игровыми паками ХОД

Стабильная коллекция **0.4.0**, companion приложение **0.15.0**. [Руководство автора](docs/AUTHORING.md) описывает текущие engineApi 1 / viewApi 2. Версии отдельных игр независимы от версии коллекции.

- Проверьте корень Git, ветку и имеющиеся изменения; сохраняйте постороннюю работу. Настройка окружения описана в [docs/CODEX-CLOUD.md](docs/CODEX-CLOUD.md).
- Каждая игра полностью принадлежит `packs/<id>/`: `manifest.json`, `rules.js`, `view.js`, `styles.css`, необязательные звуки и ресурсы. `manifest.json` — источник метаданных; `manifest.js` генерируется, не редактируйте его отдельно.
- Приложение и общие механизмы находятся в отдельном `boardgame-playroom`. Не копируйте его ядро в игры. Используйте документированные API правил, UI/source/target, ввода и событий; общую функциональность предлагайте в репозитории приложения.
- Не меняйте содержимое опубликованной версии: обновления получают новую версию пака. `engineApi` и `stateVersion` меняются осознанно, с проверкой совместимости. Старые сохранения должны оставаться доступны через прежний пак.
- Правила должны сохранять корректную очередность, легальные действия, автоматические показатели, воспроизводимость и приватность. View не раскрывает скрытые карты, не обходит выбор цвета/цели и не вычисляет правила повторно. Стили ограничивайте компонентами своего пака.
- Сохраняйте ресурсы игры в её паке, без внешнего CDN. Не коммитьте `dist/`, временные экспорты, личные сохранения, секреты или материалы соседних проектов.

## Проверки

- Самостоятельно: `bash scripts/codex/setup.sh`, затем `bash scripts/codex/check.sh`. Для сборки нужны Python 3.9+ и Node.js 22+ для проверки JS; npm этому репозиторию не нужен.
- Для правил и интерфейса нужна совместная проверка: `bash scripts/codex/setup.sh --app-dir PATH`, затем `bash scripts/codex/check.sh --full --app-dir PATH`, где PATH — корень checkout приложения. Скрипт использует проверку приложения и именно текущие исходники паков.
- Если приложение недоступно, проверьте собственную сборку и JS, но явно укажите, что gameplay/browser suite не выполнен. Самостоятельная сборка не доказывает работу на телефоне.
- В изменённой игре проверяйте наборы правил, скрытую/открытую руку, ботов и передачу телефона, легальные цели, replay. Для UI дополнительно проверьте 320/390 px в портрете и короткий landscape, читаемость всех нужных значений, touch/drag/swipe, отсутствие обрезки поля/кнопок/руки. Добавляйте точечные регрессии в существующие проверки приложения по необходимости.

## Ветки и результат

`main` — релизы, `dev` — интеграция; обычные PR направляются в `dev`, выпуск — `dev` → `main` по [CONTRIBUTING.md](CONTRIBUTING.md). Новую задачу обычно начинайте от `dev`. Если Cloud уже создал рабочую ветку, продолжайте её без принудительного переключения или сброса.

Сообщайте точные проверенные команды и ограничения. Не утверждайте, что облачное окружение создано, PR объединён или релиз опубликован, если выполнена только подготовка репозитория.

Релизный PR dev → main объединяется merge-коммитом с последующим fast-forward dev; обычные task PR — squash. Не force-reset общие ветки. После выпуска остаются main/dev и исторические теги.
